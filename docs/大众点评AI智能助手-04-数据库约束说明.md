# 大众点评 AI 智能助手数据库约束说明

## 1. 存储职责

| 存储 | 职责 | 一致性定位 |
| --- | --- | --- |
| MySQL 8 | 用户权限、商家、点评、知识库元数据、会话、反馈、模型与审计 | 业务事实源，强一致事务 |
| OpenSearch | Chunk 的 BM25/向量混合检索、过滤、聚合 | 可重建的搜索投影，最终一致 |
| Redis | 会话热数据、缓存、限流、分布式锁、任务进度 | 可过期或可恢复，不作为唯一事实源 |
| 对象存储/本地卷 | 原文件、版本文件、JSONL、模型 Adapter、图表 | 数据库存路径、哈希和元数据 |

## 2. 全局建模约定

- MySQL 使用 `utf8mb4`、`utf8mb4_0900_ai_ci`，事务表使用 InnoDB。
- 主键采用 UUID v7；数据库字段使用 `BINARY(16)`，API 层转换为标准 UUID 字符串。
- 表名和字段名使用小写蛇形；布尔值使用 `TINYINT(1)`；枚举在数据库使用 `VARCHAR` + `CHECK`，避免 MySQL `ENUM` 迁移困难。
- 所有业务表至少包含 `id`、`created_at`、`updated_at`；可编辑表包含 `version` 乐观锁字段。
- 需要逻辑删除的表包含 `deleted_at`，默认查询必须排除已删除记录。
- 时间统一保存 UTC 的 `DATETIME(6)`；展示时由前端按时区转换。
- 金额保存为整数分 `BIGINT`，经纬度使用 `DECIMAL(10,7)`，评分使用 `DECIMAL(3,2)`。
- 大文本和 JSON 不参与普通 B-Tree 索引；JSON 字段必须有 Pydantic/JSON Schema 校验。

## 3. 核心实体关系

```text
users ──< user_roles >── roles ──< role_permissions >── permissions
  │
  ├──< conversations ──< messages ──< message_sources >── chunks
  │                           └──< feedback
  └──< audit_logs

knowledge_bases ──< documents ──< document_versions ──< chunks
       │                                      └──< indexing_jobs
       └──< knowledge_base_acl

merchants ──< merchant_users
    ├──< menus/menu_items
    ├──< reviews ──< review_analyses
    └──< merchant_metric_daily

datasets ──< fine_tuning_jobs ──< model_versions ──< model_deployments
```

## 4. 表级约束

### 4.1 用户、角色与授权

#### `users`

关键字段：`username`、`email`、`password_hash`、`status`、`login_failed_count`、`locked_until`、`deleted_at`。

- `UNIQUE(username)`、`UNIQUE(email)`；写入前统一 trim 和小写规范化。
- `status CHECK IN ('ACTIVE','DISABLED','LOCKED')`。
- `password_hash` 只保存 Argon2id/bcrypt 哈希，禁止可逆加密和明文。
- 删除用户采用逻辑删除；历史消息、反馈、审计记录不得级联物理删除。

#### `roles`、`permissions`、`user_roles`、`role_permissions`

- `roles.code`、`permissions.code` 全局唯一且发布后不可修改。
- 关联表使用联合唯一约束，防止重复授权。
- 系统预置角色使用 `is_system=1`，不得删除。
- 资源范围另存 `resource_grants(subject_type, subject_id, resource_type, resource_id, action)`，并对五元组设唯一约束。

### 4.2 商家与点评

#### `merchants`

关键字段：`name`、`category_id`、`address`、`longitude`、`latitude`、`avg_price_cent`、`rating`、`business_status`、`last_verified_at`。

- `longitude BETWEEN -180 AND 180`，`latitude BETWEEN -90 AND 90`。
- `avg_price_cent >= 0`；`rating BETWEEN 0 AND 5`。
- `business_status CHECK IN ('OPEN','CLOSED','SUSPENDED','UNKNOWN')`。
- 推荐查询建立 `(category_id, business_status)`、`(region_id, business_status)` 索引；空间查询可增加 `POINT SRID 4326` 的 SPATIAL INDEX。

#### `reviews`

关键字段：`merchant_id`、`author_ref`、`content`、`rating`、`reviewed_at`、`source_type`、`source_review_id`、`status`、`content_hash`。

- `FOREIGN KEY merchant_id` 使用 `RESTRICT`，商家存在历史点评时不得物理删除。
- `(source_type, source_review_id)` 唯一；无外部 ID 时以 `(merchant_id, content_hash, reviewed_at)` 去重。
- `rating BETWEEN 0 AND 5`；`content` 非空且规范化后长度 1—10000。
- `status CHECK IN ('PUBLISHED','PENDING','REJECTED','DELETED')`；只有 `PUBLISHED` 可进入在线检索。

#### `review_analyses`

- `(review_id, task_type, model_version_id)` 唯一，保证同一模型结果幂等。
- `sentiment CHECK IN ('POSITIVE','NEUTRAL','NEGATIVE')`；`confidence BETWEEN 0 AND 1`。
- `labels_json`、`reason_codes_json` 必须通过应用层 JSON Schema 校验。
- 分析结果不覆盖历史记录；新模型写新版本，`is_current` 由事务内切换。

### 4.3 知识库、文档与 Chunk

#### `knowledge_bases`

- 同一租户下有效知识库名称唯一：应用层规范化名称并维护 `normalized_name`，唯一约束 `(tenant_id, normalized_name, active_flag)`。
- `status CHECK IN ('ACTIVE','ARCHIVED','DELETED')`。
- `chunk_size BETWEEN 100 AND 4000`，`chunk_overlap >= 0 AND chunk_overlap < chunk_size`。
- 切换 Embedding 模型只影响新版本；已有 Chunk 必须通过重建任务后才能切换线上索引别名。

#### `documents`

- `(knowledge_base_id, source_type, source_key)` 唯一，防止同数据源重复登记。
- `status CHECK IN ('UPLOADED','PARSING','INDEXING','READY','FAILED','ARCHIVED','DELETED')`。
- 文件 SHA-256 为 64 位十六进制；同知识库相同哈希默认复用或创建显式新版本。
- 删除文档不级联删除历史版本和任务；先标记删除，再发出索引删除事件。

#### `document_versions`

- `(document_id, version_no)` 唯一；`version_no > 0` 且单调递增。
- 文件路径、SHA-256、解析器版本、清洗配置快照、切分配置快照不可变。
- 每个文档仅一条 `is_current=1`，应用通过事务和唯一辅助字段保证。

#### `chunks`

关键字段：`document_version_id`、`chunk_no`、`content`、`content_hash`、`token_count`、`page_number`、`metadata_json`、`embedding_model_id`、`index_status`。

- `(document_version_id, chunk_no)` 唯一；`chunk_no >= 0`。
- `content` 非空；`token_count > 0`；`page_number` 为空或 `>= 1`。
- `(document_version_id, content_hash)` 可作为去重索引。
- MySQL 不保存大规模向量；只保存模型 ID 和 OpenSearch 文档 ID。必要的离线向量快照存对象存储。

### 4.4 会话、消息、引用与反馈

#### `conversations`

- `owner_user_id` 必填；访问必须校验所有权或管理权限。
- `status CHECK IN ('ACTIVE','ARCHIVED','DELETED')`。
- `memory_backend CHECK IN ('REDIS','MYSQL')`，Redis 内容失效时可从 MySQL 消息恢复。

#### `messages`

- `(conversation_id, sequence_no)` 唯一；序号在事务内递增。
- `role CHECK IN ('SYSTEM','USER','ASSISTANT','TOOL')`。
- `status CHECK IN ('STREAMING','COMPLETED','FAILED','CANCELLED')`。
- Assistant 消息从 `STREAMING` 完成后才可用于训练；失败的部分文本保留但不得默认进入上下文。
- `parent_message_id` 用于回滚/分支；必须属于同一 conversation。

#### `message_sources`

- `(message_id, chunk_id)` 唯一；`rank > 0`；`score BETWEEN 0 AND 1`（若算法原始得分不在此范围，应另存 raw_score）。
- 保存生成当时的 `content_snapshot` 和 `source_location_snapshot`，避免源文档更新后无法审计。

#### `feedback`

- `(user_id, message_id)` 仅一条当前有效反馈；更新时递增 `version`，历史写入 `feedback_audits`。
- `rating CHECK IN (-1, 1)`；踩反馈可要求至少一个 reason_code 或 correction。
- correction 最大 4000 字，入库前执行敏感信息检测和脱敏标记。

### 4.5 模型、数据集与训练

#### `datasets`

- `dataset_hash` 全局唯一；数据集发布后内容不可变。
- 保存筛选条件、脱敏规则版本、样本数、train/validation/test 切分和对象存储 URI。
- `status CHECK IN ('BUILDING','READY','REJECTED','ARCHIVED')`；只有 READY 可用于训练。

#### `fine_tuning_jobs`

- 关联 `base_model_version_id` 与 `dataset_id`，训练参数以不可变 JSON 快照保存。
- 状态只允许 `PENDING → RUNNING → SUCCEEDED|FAILED|CANCELLED`。
- 保存随机种子、Git commit、容器镜像摘要、Transformers/PEFT 版本以支持复现。
- 同一 `dataset_hash + base_model + hyperparameter_hash` 可设唯一幂等键。

#### `model_versions` 与 `model_deployments`

- `model_versions(model_id, version)` 唯一；Adapter 路径和 SHA-256 必填。
- 未通过评测门禁的版本不得进入 `STAGING/PRODUCTION`。
- 同一场景和环境只允许一个全量 ACTIVE 部署；灰度部署的流量比例总和不得超过 100%。
- 发布、回滚必须写审计日志，保留操作者和原因。

### 4.6 任务、Outbox 与审计

#### `async_tasks`

- `task_type`、`status`、`progress`、`attempt_count`、`max_attempts`、`error_code`、`heartbeat_at`。
- `progress BETWEEN 0 AND 100`；SUCCEEDED 必须为 100。
- Worker 以 `locked_by`、`locked_until` 防止重复消费；任务处理逻辑仍须幂等。

#### `outbox_events`

- 业务事务内写入事件；事件发布成功后更新 `published_at`。
- `event_id` 唯一；消费者按 event_id 去重。
- 文档索引相关事件包含 document_version_id，不传大段原文。

#### `audit_logs`

- 只追加不更新；记录 actor、action、resource、before/after 摘要、IP、request_id、结果和时间。
- 密码、Token、密钥、完整提示词隐私内容不得写入。
- 普通业务外键不应级联删除审计日志。

## 5. 外键删除策略

| 父实体 | 子实体 | 策略 | 原因 |
| --- | --- | --- | --- |
| knowledge_bases | documents | RESTRICT + 逻辑删除 | 避免误删整库历史 |
| documents | document_versions | RESTRICT | 版本用于审计与回滚 |
| document_versions | chunks | RESTRICT/后台清理 | 先删除搜索投影，再按保留策略清理 |
| merchants | reviews | RESTRICT | 保留评价事实 |
| conversations | messages | RESTRICT + 逻辑删除 | 保留反馈和审计关联 |
| messages | message_sources/feedback | RESTRICT | 保证答案溯源和训练来源 |
| users | user_roles | CASCADE | 纯关联数据可清理 |

禁止在核心历史链路使用无条件 `ON DELETE CASCADE`。

## 6. 索引设计

### 6.1 MySQL 推荐索引

- `documents(knowledge_base_id, status, created_at DESC)`。
- `chunks(document_version_id, chunk_no)`、`chunks(index_status, updated_at)`。
- `reviews(merchant_id, status, reviewed_at DESC)`。
- `review_analyses(review_id, task_type, is_current)`。
- `messages(conversation_id, sequence_no)`。
- `feedback(message_id, rating, created_at)`。
- `async_tasks(status, task_type, created_at)`。
- `audit_logs(actor_id, created_at)`、`audit_logs(resource_type, resource_id, created_at)`。

索引以真实查询和 `EXPLAIN` 为依据，避免为低选择性字段建立单列索引。

### 6.2 OpenSearch Chunk 索引

建议按租户/环境使用版本化索引：`local-life-chunks-v{n}`，通过别名 `local-life-chunks-read`、`local-life-chunks-write` 零停机切换。

```json
{
  "settings": {
    "index.knn": true,
    "analysis": {
      "analyzer": {
        "zh_search": {"type": "custom", "tokenizer": "standard", "filter": ["lowercase"]}
      }
    }
  },
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "chunk_id": {"type": "keyword"},
      "tenant_id": {"type": "keyword"},
      "knowledge_base_id": {"type": "keyword"},
      "document_id": {"type": "keyword"},
      "document_version_id": {"type": "keyword"},
      "merchant_id": {"type": "keyword"},
      "content": {"type": "text", "analyzer": "zh_search"},
      "content_vector": {"type": "knn_vector", "dimension": 512},
      "source_type": {"type": "keyword"},
      "source_location": {"type": "keyword", "index": false},
      "category_ids": {"type": "keyword"},
      "price_cent": {"type": "long"},
      "location": {"type": "geo_point"},
      "business_status": {"type": "keyword"},
      "valid_from": {"type": "date"},
      "valid_to": {"type": "date"},
      "updated_at": {"type": "date"}
    }
  }
}
```

`dimension` 必须与当前 Embedding 模型一致。模型变更时创建新索引，禁止修改已有字段维度。所有查询强制过滤 tenant、知识库权限、有效期和业务状态。

## 7. Redis Key 规范

| Key | 类型 | TTL | 说明 |
| --- | --- | --- | --- |
| `sess:{conversation_id}` | Hash/List | 24 h，可配置 | 最近上下文缓存 |
| `rate:{subject}:{route}:{window}` | String | 窗口期 | 限流计数 |
| `task:{task_id}` | Hash | 24 h | 实时任务进度，MySQL 为事实源 |
| `lock:index:{document_version_id}` | String | 任务超时+余量 | 索引互斥锁 |
| `cache:search:{scope_hash}:{query_hash}` | String | 5 min | 权限范围参与缓存键 |

Redis Key 不得包含邮箱、手机号或原始查询文本；使用 ID 或哈希。

## 8. 事务与一致性规则

1. 用户、反馈、模型发布等操作在单个 MySQL 事务内完成。
2. MySQL 与 OpenSearch 不做分布式事务；通过 Transactional Outbox 实现最终一致。
3. 索引消费者使用 `document_version_id + chunk_no` 作为确定性 OpenSearch `_id`，重复写为覆盖。
4. 只有全部 Chunk 写入成功并校验数量后，文档状态才变为 READY。
5. 删除流程先标记不可见，再异步删除索引；即使索引删除失败，在线查询的有效状态过滤仍能阻止召回。
6. 定时对账比较 MySQL READY Chunk 数与 OpenSearch 数量，差异生成修复任务。

## 9. 数据保留与隐私

- 原始对话默认保存 180 天，可由管理员调整；审计日志建议保存不少于 1 年。
- 用户申请删除时，删除可识别信息并匿名化必须保留的统计/审计关联。
- 训练数据集不直接引用可变业务表，生成时固化、脱敏、哈希并记录来源许可。
- 对象存储文件按数据分类设置生命周期；模型和数据集删除采用审批及延迟清理。
- 数据库备份需加密，定期恢复演练；生产数据不得直接复制到开发环境。

## 10. 迁移与验收

- 使用 Alembic 管理迁移；每个迁移提供 upgrade，破坏性变更提供分阶段兼容方案。
- CI 在空库执行全量迁移，并从上一发布版本执行增量迁移测试。
- 数据库验收覆盖唯一、检查、外键、逻辑删除、乐观锁、幂等和并发序号测试。
- OpenSearch 验收覆盖 mapping 严格模式、向量维度、权限过滤、别名切换和索引对账。

## 11. 物理数据库具体设计

本节在前述约束基础上给出可落地的 MySQL 8 物理模型。MySQL 是业务事实源；OpenSearch、Redis 和对象存储均为投影、缓存或大文件存储，不替代 MySQL 的事务记录。

### 11.1 数据库与字符集

```sql
CREATE DATABASE IF NOT EXISTS local_life_ai
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

USE local_life_ai;
```

统一约定：

- 主键在 MySQL 使用 `BINARY(16)` 保存 UUID v7，应用通过 `UUID_TO_BIN(uuid, 1)` 和 `BIN_TO_UUID(id, 1)` 转换。
- 金额单位为分，类型为 `BIGINT UNSIGNED`；评分使用 `DECIMAL(3,2)`。
- 所有时间保存 UTC，使用 `DATETIME(6)`。
- 需要更新的聚合/配置表包含 `version INT UNSIGNED` 作为乐观锁。
- 需要逻辑删除的实体包含 `deleted_at DATETIME(6) NULL`。
- JSON 字段使用原生 `JSON`，写入前必须通过应用层 Pydantic/JSON Schema 校验。

### 11.3 公共审计字段

除纯关联表和只追加日志表外，业务表统一包含：

| 字段 | 类型 | 空值/默认 | 说明 |
| --- | --- | --- | --- |
| `id` | `BINARY(16)` | NOT NULL | UUID v7 主键 |
| `created_at` | `DATETIME(6)` | NOT NULL DEFAULT CURRENT_TIMESTAMP(6) | 创建时间 |

### 11.10 核心 MySQL DDL 示例

以下 DDL 展示最核心的表结构和约束；实际迁移由 Alembic 按依赖顺序生成，约束名必须显式命名。

```sql
CREATE TABLE users (
  id BINARY(16) NOT NULL,
  department_id BINARY(16) NULL,
  username VARCHAR(64) NOT NULL,
  normalized_username VARCHAR(64) NOT NULL,
  email VARCHAR(254) NULL,
  normalized_email VARCHAR(254) NULL,
  password_hash VARCHAR(255) NOT NULL,
  display_name VARCHAR(128) NOT NULL,
  status VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
  login_failed_count SMALLINT UNSIGNED NOT NULL DEFAULT 0,
  locked_until DATETIME(6) NULL,
  last_login_at DATETIME(6) NULL,
  version INT UNSIGNED NOT NULL DEFAULT 1,
  created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  updated_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
    ON UPDATE CURRENT_TIMESTAMP(6),
  deleted_at DATETIME(6) NULL,
  PRIMARY KEY (id),
  CONSTRAINT uq_users_username UNIQUE (normalized_username),
  CONSTRAINT uq_users_email UNIQUE (normalized_email),
  CONSTRAINT ck_users_status CHECK (status IN ('ACTIVE','DISABLED','LOCKED')),
  INDEX ix_users_department_status (department_id, status)
) ENGINE=InnoDB;

CREATE TABLE knowledge_bases (
  id BINARY(16) NOT NULL,
  department_id BINARY(16) NULL,
  owner_id BINARY(16) NOT NULL,
  name VARCHAR(200) NOT NULL,
  normalized_name VARCHAR(200) NOT NULL,
  description TEXT NULL,
  embedding_model_version_id BINARY(16) NOT NULL,
  chunk_size SMALLINT UNSIGNED NOT NULL DEFAULT 500,
  chunk_overlap SMALLINT UNSIGNED NOT NULL DEFAULT 80,
  status VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
  version INT UNSIGNED NOT NULL DEFAULT 1,
  created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  updated_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
    ON UPDATE CURRENT_TIMESTAMP(6),
  deleted_at DATETIME(6) NULL,
  PRIMARY KEY (id),
  CONSTRAINT fk_kb_owner FOREIGN KEY (owner_id) REFERENCES users(id),
  CONSTRAINT ck_kb_chunk_size CHECK (chunk_size BETWEEN 100 AND 4000),
  CONSTRAINT ck_kb_overlap CHECK (chunk_overlap < chunk_size),
  CONSTRAINT ck_kb_status CHECK (status IN ('ACTIVE','ARCHIVED','DELETED')),
```

### 11.11 MySQL 与 OpenSearch 字段映射

| MySQL 来源 | OpenSearch 字段 | 作用 | 同步规则 |
| --- | --- | --- | --- |
| `chunks.id` | `chunk_id` | 稳定标识 | UUID 字符串 |
| `documents.id` | `document_id` | 文档过滤/溯源 | 写入时展开 |
| `document_versions.id` | `document_version_id` | 版本隔离 | 必填 |
| `knowledge_bases.id` | `knowledge_base_id` | 权限过滤 | 必填 |
| `chunks.content` | `content` | BM25 检索 | 原文 |
| Embedding 推理结果 | `content_vector` | k-NN 检索 | 维度由模型决定，不落 MySQL |
| `chunks.metadata_json.merchant_id` | `merchant_id` | 商家过滤 | 无商家则为空 |
| `merchants.category_id` | `category_ids` | 分类过滤 | 可展开祖先分类 |
| `merchants.avg_price_cent` | `price_cent` | 价格过滤 | 商家更新触发重投影 |
| 商家经纬度 | `location` | 距离过滤 | `geo_point` |
| `merchants.business_status` | `business_status` | 营业状态过滤 | 变更触发局部更新 |
| 文档/菜单有效期 | `valid_from`、`valid_to` | 时效硬过滤 | 查询必须过滤过期内容 |

OpenSearch 只保存搜索所需冗余字段；MySQL 更新后通过 Outbox 事件刷新投影。对话引用始终保存 MySQL `message_sources` 快照，不能只依赖可变的 OpenSearch 文档。

### 11.12 Redis 与数据库恢复关系

| Redis 数据 | MySQL 恢复来源 | 丢失后的行为 |
| --- | --- | --- |
| 最近会话上下文 | `conversations`、`messages` | 按 sequence_no 重建最近 N 轮 |
| 任务实时进度 | `async_tasks` | 返回数据库最后持久化进度 |
| 检索缓存 | 无需恢复 | 缓存未命中后重新检索 |
| 限流计数 | 无需恢复 | 短暂丢失只影响当前窗口 |
| 索引锁 | `async_tasks` 心跳辅助判断 | 锁过期后由幂等任务接管 |

### 11.13 建表和迁移顺序

1. `departments`、`users`、角色权限和授权表。
2. 商家分类、商家、商家用户、菜单和点评表。
3. `model_definitions`、基础 `model_versions`。
4. 知识库、文档、版本和 Chunk 表。
5. 会话、消息、引用、反馈和反馈审计表。
6. 分析结果、商家聚合、提示词、数据集、训练和部署表。
7. 异步任务、Outbox、审计表及全部二级索引。
8. 初始化角色、权限、基础模型、默认提示词和系统参数。
9. 创建 OpenSearch 索引模板和别名，执行 MySQL→OpenSearch 首次投影。

每次迁移应满足“扩展字段 → 双写/回填 → 切换读取 → 删除旧字段”的兼容流程，禁止在同一生产发布中直接删除仍被旧版本代码读取的字段。

### 11.14 数据库设计验收清单

- 空库可以从 Alembic revision 0 完整升级到最新版本。
- 上一发布版本可以增量迁移，迁移失败可安全停止且不破坏已有数据。
- 所有状态字段、金额、评分、进度和版本号的 CHECK 约束生效。
- 所有唯一约束均有并发写入测试，而不仅是顺序测试。
- 外键删除策略符合第 5 节，不存在核心历史链路的误级联删除。
- 查询知识库、点评、会话、任务和审计日志时，`EXPLAIN` 命中预期索引。
- MySQL 与 OpenSearch 对账任务可以发现缺失、多余和版本错误的 Chunk。
- Redis 清空后，会话和任务的关键事实仍可从 MySQL 恢复。
- 数据集、提示词和模型版本发布后不可变，灰度比例和发布门禁约束生效。
- 备份恢复演练可以恢复 MySQL、对象存储引用和 OpenSearch 重建所需元数据。
