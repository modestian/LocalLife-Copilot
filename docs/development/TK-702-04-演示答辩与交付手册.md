# TK-702-04 演示、答辩与交付手册

## 1. 目的与范围

本文是 ST-702「全链路质量验收与演示」的现场执行脚本和交付清单，覆盖管理员知识摄取、普通用户探店/RAG/引用/反馈、商家趋势和越权、模型评测信息与回滚，以及无结果和异步任务失败两条错误路径。

本文以以下已纳入版本控制的材料为准：

- [确定性演示数据（TK-702-01）](ST-702-确定性演示数据.md)：固定账号、角色、商家、点评、文档和问题集。
- [Playwright 核心链路 E2E（TK-702-02）](ST-702-Playwright核心链路E2E.md)：浏览器端角色与错误态自动化证据。
- [全新环境三轮回归报告（TK-702-03）](../reports/2026-07-22-TK-702-03全新环境回归报告.md)：清空业务卷后连续三轮的真实服务证据。
- [API 接口规范](../project/大众点评AI智能助手-03-API接口规范.md)：上传任务、检索、反馈、商家分析和模型治理契约。
- [数据库约束说明](../project/大众点评AI智能助手-04-数据库约束说明.md)：异步任务状态、引用快照、反馈审计和模型发布/回滚审计约束。

现场不直接修改数据库。所有数据仅通过迁移、确定性种子和 API 写入；模型回滚会新建部署/审计记录，而不是改写历史版本。

## 3. 演示前执行脚本

### 3.1 标准准备（非破坏性）

在仓库根目录执行。`Read-Host` 的输入不回显；变量仅存在于当前 PowerShell 会话。

```powershell
$env:DEMO_SEED_PASSWORD = Read-Host -Prompt '请输入本次演示临时密码'
docker compose up --build --wait
docker compose exec -T -e DEMO_SEED_PASSWORD api python -m app.cli.seed_demo_data
Invoke-RestMethod http://127.0.0.1:3000/health/ready
```

预期种子摘要为 `3 users, 2 merchants, 12 reviews, 2 documents, 3 standard questions`，就绪接口返回 `status: ready`。若服务已构建且未变更，可把第一条 Compose 命令替换为 `docker compose up -d --wait`。

打开 <http://127.0.0.1:3000>；API 与 Swagger 入口分别为 <http://127.0.0.1:18000/docs> 和 <http://127.0.0.1:3000/docs>。

### 3.2 重新开始（仅在确认可删除本机演示业务数据时）

现场需要恢复到完全干净的基线、或需要复核三轮全新环境结论时，先获得演示负责人确认，再运行下列命令。它会永久删除本项目本机 Compose 卷中的 MySQL、Redis 与 OpenSearch 数据，绝不能用于生产环境。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/run_tk702_fresh_regression.ps1 -Rounds 3
```

该脚本每轮执行迁移、索引初始化、种子、真实上传/检索/反馈/商家权限/模型回滚和 Playwright；证据输出到 `artifacts/tk-702-03/`。已提交的三轮结果见 [TK-702-03 报告](../reports/2026-07-22-TK-702-03全新环境回归报告.md)。

## 4. 现场演示与答辩步骤

每一步均应先说明“谁在做什么、系统如何限制”，再展示可见结果。不要展示或口述临时密码、Bearer Token、完整请求头或日志中的敏感上下文。

### 步骤 A：管理员上传并等待索引（约 3 分钟）

1. 使用 `demo-admin` 登录，打开 `/admin/knowledge-bases/70200000-0000-4000-8000-000000000010`。
2. 指出已有文档/Chunk 统计和管理员可编辑权限；选择 [固定上传资料](demo-assets/tk-702-04-upload.md) 上传。
3. 说明上传接口返回的是任务 ID，不把“已接收”当作“已可检索”。页面会轮询 `/api/v1/tasks/{task_id}`，依次展示 `PENDING`、`RUNNING`/`INDEXING` 和 `SUCCEEDED`。
4. 任务进度到 100% 后，展示成功任务卡和文档列表更新。若任务变为 `FAILED` 或 `CANCELLED`，停止现场断言并转到“步骤 F”的自动化错误证据和降级方案。

验收口径：任务只有在所有 Chunk 写入并校验后才进入 `SUCCEEDED`/文档 `READY`；该规则来自数据库文档的异步任务与索引一致性约束。

### 步骤 B：普通用户探店、引用跳转与反馈（约 4 分钟）

1. 退出并用 `demo-user` 登录，打开 `/app`，选择会话“清河面馆午餐咨询”。
2. 展示答案“适合。资料显示双人小菜套餐分量充足；午餐高峰建议错峰以避开排队。”，并对该助手消息点击有帮助，确认反馈提交成功。接口为 `POST /api/v1/chat/feedback`，包含固定的会话 ID、消息 ID、`rating: 1` 和 `HELPFUL` 原因码。
3. 执行下列带浏览器窗口的 Playwright 用例，展示普通用户在真实页面中展开引用抽屉、核对“清河面馆探店资料”和重点片段、点击链接到知识库文档；同一用例也验证无结果兜底。来源是生成时保存的引用快照，而非临时模型文本。

```powershell
Push-Location frontend
npm run test:e2e -- st-702-core-flows.spec.ts --project=desktop-chromium --headed
Pop-Location
```

答辩要点：同一用户对同一消息只有一条当前有效反馈；重复提交更新版本并保留反馈审计，符合数据库约束。

### 步骤 C：商家趋势与越权拦截（约 3 分钟）

1. 用 `demo-merchant` 登录，打开 `/merchant/70200000-0000-4000-8000-000000000020`。
2. 展示情感趋势、负面原因和可下钻点评，说明数据由固定的 12 条点评构成，不使用生产数据。
3. 在地址栏改为 `/merchant/70200000-0000-4000-8000-000000000022`。页面应显示“当前账号未获得该商家的资源授权”，不加载商家分析。
4. 如需给出可复核的服务端证据，商家账号请求 `GET /api/v1/merchants/{未授权ID}/analytics/sentiment-trend` 应返回 404；三轮回归脚本已对此断言。

答辩要点：资源范围来自 `resource_grants`，不是只依赖前端隐藏菜单；越权资源以 404 处理，避免暴露资源是否存在。

### 步骤 D：管理员查看模型指标并执行回滚（约 3 分钟）

1. 用 `demo-admin` 登录，打开 `/admin/models`，点击“刷新模型版本”，选择 `demo-sentiment-v2`。
2. 展示模型状态、产物 SHA-256、Adapter URI 和固定评测指标 `accuracy: 0.95`；说明 v2 是种子中的 `APPROVED` 基线版本。
3. 当前前端模型页刻意不伪造审批或回滚状态，因此用 Swagger 或下列 PowerShell 调用真实治理接口。将 `$adminToken` 替换为本次管理员登录响应中的短期 token，且不得录屏或写入文件。

```powershell
$rollbackBody = @{
  scene = 'sentiment'
  environment = 'demo'
  reason = 'TK-702-04 现场验收：验证受审计模型回滚'
} | ConvertTo-Json -Compress

Invoke-RestMethod `
  -Method Post `
  -Uri 'http://127.0.0.1:18000/api/v1/models/70200000-0000-4000-8000-000000000032/rollback' `
  -Headers @{ Authorization = "Bearer $adminToken" } `
  -ContentType 'application/json' `
  -Body $rollbackBody
```

4. 展示响应中的 `data.action: ROLLBACK`，再调用 `GET /api/v1/models/deployments?scene=sentiment&environment=demo` 或在 Swagger 中查看部署记录。回滚原因、操作人、时间和结果必须可审计。

答辩要点：模型版本和部署记录是不可覆盖的历史；回滚只允许回到已经成功部署过的目标。`demo-sentiment-v1` 是归档版本，不作为此基线的回滚目标。

### 步骤 E：无结果兜底（约 2 分钟）

1. 展示 [questions.json](../../backend/demo_data/questions.json) 中 `q-003`：“附近有提供火星料理的店吗？”。
2. 若步骤 B 已执行，无须重复运行；其中的普通用户场景会在真实页面中验证空推荐、无引用时的“没有足够的可信检索证据”兜底提示，不把编造推荐展示为结果。

```powershell
Push-Location frontend
npm run test:e2e -- st-702-core-flows.spec.ts
Pop-Location
```

该错误路径使用 Playwright 路由契约桩，以稳定复演前端安全兜底；真实检索、引用和上传/索引的服务级证据由三轮回归脚本提供。不得为了制造空结果而删除演示知识或手动篡改索引。

### 步骤 F：任务失败与可重试证据（约 1 分钟）

继续使用上一步 Playwright 命令。其管理员失败场景返回受控的 `SEARCH_BACKEND_UNAVAILABLE`，断言页面展示错误详情、失败任务卡和“重试”按钮，并确认 `POST /api/v1/tasks/{task_id}/retry` 被调用。

现场不停止 OpenSearch 或 Worker 来“制造”失败，这会破坏其余验收链路；失败截图、trace 与日志由 Playwright 在失败时保留到 `frontend/test-results/`，回归脚本同时保留每轮 `playwright.log`、`compose.log` 和 `summary.json`。

## 5. 外部模型不可用时的降级预案

| 情况 | 现场动作 | 可继续展示的真实证据 | 禁止事项 | 恢复条件 |
| --- | --- | --- | --- | --- |
| 外部/模型网关不可用，`/health/ready` 为 503 | 明确宣布实时生成暂停，保留故障响应或健康检查截图。 | 已种子的会话、持久化引用、商家分析、反馈、模型指标/回滚 API，以及 Playwright 路由契约 E2E。 | 不伪造回答、不把缓存答案标为实时生成。 | 模型网关恢复且 `/health/ready` 返回 `ready` 后，再演示实时对话。 |
| OpenSearch 或 Worker 不可用 | 不执行上传完成或实时检索断言；展示任务失败/重试 E2E 与此前三轮证据。 | 管理员失败态、错误码、可重试操作和回归日志。 | 不手改任务状态、文档状态或索引数据。 | 依赖健康后重新上传固定文件，并等待任务 `SUCCEEDED`。 |
| 浏览器或前端构建环境不可用 | 用 API/Swagger 复核种子、趋势、反馈和回滚；引用三轮回归报告。 | API 响应、`summary.json`、`compose.log`。 | 不声称已完成浏览器 E2E。 | 安装 Chromium/依赖后重跑 Playwright。 |

降级的目标是保留可验证事实，而不是将自动化桩或历史截图表述为当场的实时模型能力。

## 7. 常见提问的简答

| 问题 | 回答 |
| --- | --- |
| 为什么不直接查表或改表？ | 用户、反馈、模型和审计均是业务事实源；直接改表会绕过权限、事务、异步状态和审计约束。 |
| 为什么上传后必须等待？ | 上传仅表示请求受理；只有任务成功、Chunk 校验完成后，文档才可作为可检索证据。 |
| 无结果时为何不推荐相似商家？ | 没有足够可信引用时，系统明确兜底而不是生成无证据推荐。 |
| 如何证明越权不是前端假象？ | 回归脚本使用商家 token 调真实趋势 API，未授权资源返回 404。 |
| 前端为何不用一个“回滚成功”提示？ | 前端不会伪造服务端治理状态；现场调用有权限校验和审计的真实回滚 API，并检查 `ROLLBACK` 记录。 |
