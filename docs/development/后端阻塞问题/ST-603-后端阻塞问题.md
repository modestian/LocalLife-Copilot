# ST-603 商家与模型管理：后端阻塞问题

## 当前结论

最新 `origin/main@4e71fe4` 已包含 TK-401-05 的三项口碑分析接口，当前 TK-603-01 分支也已通过 Fast-forward 同步到该基线。基础接口可以开始本地联调，但权限、特征聚合、归因趋势、分页和分析追溯字段仍存在后端缺口。

当前已提供的实际路径：

- `GET /api/v1/merchants/{merchant_id}/analytics/sentiment-trend`
- `GET /api/v1/merchants/{merchant_id}/analytics/negative-reasons`
- `GET /api/v1/merchants/{merchant_id}/analytics/reviews`

## 问题清单

| 优先级 | 后端问题 | 前端影响 | 当前前端处理 | 解除阻塞标准 |
| --- | --- | --- | --- | --- |
| P0 | analytics router 没有用户认证和 `MERCHANT` 资源范围依赖 | 知道 merchant_id 的调用者可能越权读取其他商家的分析和原点评 | 商家页面按 `resource_scopes` 隐藏未授权商家，并处理 403；这不是安全边界 | 后端逐接口校验登录、角色和商家资源范围，平台管理员例外，覆盖横向越权测试 |
| P0 | 接口规范写的是 `/sentiment`、`/topics`、`/reviews`，实际实现为 `/analytics/*` | 文档、前端和后端可能继续产生两套契约 | TK-603-01 暂按已实现的 `/analytics/*` 接入 | 确定唯一正式路径并更新接口文档/OpenAPI；若迁移路径，提供兼容期或明确破坏性变更 |
| P1 | 没有方面/特征聚合接口 | 特征排行无法覆盖完整时间窗，样本超过 200 条时统计会被截断 | 从点评下钻返回的 `aspect_labels` 中聚合最近 200 条，并标注样本上限 | 提供按时间窗聚合的特征接口，至少返回 label、count、sample_count，并支持下钻条件 |
| P1 | 差评归因只有全时间窗汇总，没有日/周/月变化 | 只能展示归因排行，无法展示差评原因趋势 | 当前展示当前筛选时间窗的汇总排行 | 为归因接口增加 granularity 和 period，或提供 topics/reasons 趋势接口 |
| P1 | 点评下钻只返回数组，没有 total、next_cursor 或稳定分页元数据 | 抽屉最多显示 50 条，无法告知用户完整结果数或继续加载 | 当前限制 50 条，特征采样限制 200 条 | 返回统一分页结构和总量，保证排序稳定，并支持 sentiment、时间、特征和归因过滤 |
| P1 | 分析响应缺少 `model_version`、`prompt_version`、`generated_at`、`evidence_review_ids` | 页面无法展示分析版本和生成时间，也无法完成模型回归追溯 | 不伪造版本字段，只展示样本量和点评证据 | 按 API 规范补齐追溯元数据；点评级结果至少返回当前模型版本和证据关联 |
| P1 | 当前 `review_analyses` 实现与数据库文档的版本化模型不一致 | 无法可靠区分 task_type、当前结果和历史模型版本，重跑可能污染聚合 | 前端只能信任接口当前结果 | 对齐 `review_id + task_type + model_version_id` 唯一约束、`is_current` 切换和 labels/reasons JSON Schema |
| P2 | 低样本阈值没有后端口径 | 前端只能自行以少于 10 条显示“数据不足” | 阈值作为前端展示常量，并始终展示样本量 | 后端在聚合响应中返回 sample_count、minimum_sample_size 和 insufficient_data，统一竞品和单店口径 |

## 已解除的集成问题

## 后续 ST-603 的额外后端依赖

TK-603-02 至 TK-603-04 还依赖以下尚未在当前 `origin/main` 注册的能力：竞品统一口径比较、回复建议、经营建议与证据、消息反馈、数据集、训练任务、模型卡、审批、灰度发布和回滚接口。开始对应前端任务前，应先核对 ST-402、ST-501、ST-502 的实际接口分支和 OpenAPI，而不是继续扩展 Mock 契约。
