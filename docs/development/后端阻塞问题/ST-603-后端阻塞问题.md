# ST-603 商家与模型管理：后端阻塞问题

## 当前结论

最新 `origin/main@389c1ea` 已包含 TK-401-05 的三项口碑分析接口和 TK-603-03 前端提交；基础图表可以开始本地联调。TK-603-02 的竞品比较、回复建议和经营建议前端已按 API 文档路径接入，但后端尚未注册对应路由；同时，图表权限、特征聚合、归因趋势、分页和分析追溯字段仍存在缺口。

- `GET /api/v1/merchants/{merchant_id}/analytics/sentiment-trend`

- `GET /api/v1/merchants/{merchant_id}/analytics/reviews`

TK-603-02 需要、但当前后端尚未提供的路径：

- `POST /api/v1/merchants/compare`
- `POST /api/v1/reviews/{review_id}/reply-suggestions`
- `POST /api/v1/merchants/{merchant_id}/business-suggestions`

## TK-603-03 消息反馈接口阻塞

前端已按 `POST /api/v1/chat/feedback` 实现完成态助手消息的赞/踩、差评原因、修正答案和提交状态控件。请求携带 `conversation_id`、`message_id`、`rating`，差评可选 `reason_codes` 与最长 4000 字的 `correction`，并带 `Idempotency-Key`。

当前 `backend` 中未检索到该路由、反馈领域服务、`feedback` / `feedback_audits` 迁移或测试，因此不能进行真实联调。具体缺口如下：

- P0：实现受登录保护的反馈接口，校验消息归属与 `rating ∈ {-1, 1}`；写入 `feedback` 和只追加的 `feedback_audits`，保证 `(user_id,message_id)` 唯一、重复提交递增版本且请求幂等。
- P1：在 OpenAPI 冻结反馈原因码枚举和成功响应结构。前端目前仅使用 API 示例已明确的 `FACT_ERROR`、`OUTDATED`，因此不能擅自扩展其他原因码。
- P1：按数据库文档在入库前进行修正答案的敏感信息识别/脱敏，并保留可追溯的版本快照；前端失败时会保留用户输入供重试。

解除阻塞后，需使用本人登录账号验证：赞、踩、原因和修正答案可以提交；同一消息的重复提交会更新同一反馈记录版本；审计记录可追溯每次修改；越权消息和无效评分被拒绝。

## TK-603-04 模型生命周期接口阻塞

前端已新增受 `PLATFORM_ADMIN` / `MODEL_ADMIN` 保护的模型管理页，按接口文档接入数据集构建与查询、训练创建与查询、取消、评测、模型登记、模型列表和部署路径。页面只允许 READY 数据集创建训练任务；只有 APPROVED 模型并经过二次确认才可提交部署。审批和回滚因无正式接口不会伪造前端成功状态。

当前 `backend/app` 与测试中未检索到 `/api/v1/fine-tuning/*`、`/api/v1/models*` 的路由、领域服务、迁移或集成测试；训练脚本和评测说明文件不构成可鉴权 API。具体缺口如下：

- P0：实现数据集构建、详情、训练任务创建/详情/取消/评测/登记接口及 `datasets`、`fine_tuning_jobs`、`model_definitions`、`model_versions`、`model_deployments` 迁移。服务端须限制 READY 数据集、白名单基础模型和固定训练配置，禁止接受任意前端脚本。
- P0：实现 `MODEL_ADMIN` / `PLATFORM_ADMIN` 授权、模型版本状态机与审计；仅 APPROVED 版本可部署，同一场景只能有一个全量 ACTIVE 版本，灰度总流量不得超过 100。
- P0：补充审批和回滚 API、状态转移与回滚验证。当前 API 文档仅定义 `POST /api/v1/models/{id}/deploy`，没有审批或回滚的路径、请求体和响应契约。
- P1：冻结数据集筛选/切分请求、数据集质量报告、训练日志位置、基线与 LoRA 指标、模型卡和模型列表响应 JSON。前端类型基于数据库字段和已有示例组织，真实联调前需以 OpenAPI 为准。
- P1：实现评测门禁，验证同一冻结测试集、负面召回不下降、Macro-F1 目标、人工抽检和模型卡完整性；模型卡、审批、部署与回滚都应写入不可变审计记录。

解除阻塞后，需以真实管理员账号验证：构建的 JSONL 数据集携带 hash、脱敏版本和数据卡且 READY 后不可修改；训练可查询进度、日志、失败详情和同集指标；只有审批后的版本可灰度或全量发布；超额灰度被拒绝，回滚后新请求切回上一稳定版本并留下审计记录。

## 问题清单

| 优先级 | 后端问题 | 前端影响 | 当前前端处理 | 解除阻塞标准 |
| --- | --- | --- | --- | --- |
| P0 | analytics router 没有用户认证和 `MERCHANT` 资源范围依赖 | 知道 merchant_id 的调用者可能越权读取其他商家的分析和原点评 | 商家页面按 `resource_scopes` 隐藏未授权商家，并处理 403；这不是安全边界 | 后端逐接口校验登录、角色和商家资源范围，平台管理员例外，覆盖横向越权测试 |
| P0 | 接口规范写的是 `/sentiment`、`/topics`、`/reviews`，实际实现为 `/analytics/*` | 文档、前端和后端可能继续产生两套契约 | TK-603-01 暂按已实现的 `/analytics/*` 接入 | 确定唯一正式路径并更新接口文档/OpenAPI；若迁移路径，提供兼容期或明确破坏性变更 |
| P0 | 缺少 `POST /api/v1/merchants/compare` | TK-603-02 无法取得真实竞品比较数据 | 前端已限制选择 2～4 家竞品，并统一传递当前商家、时间窗和公共聚合口径 | 接口仅返回公开聚合数据；对所有商家使用相同时间窗、样本下限和指标公式，并返回样本量、情感、方面词和差评原因 |
| P0 | 缺少 `POST /api/v1/reviews/{id}/reply-suggestions` | 无法基于指定原点评生成可编辑回复草稿 | 前端已准备语气、方面标签和禁用承诺字段，并明确无自动发布按钮 | 返回草稿、`model_version`、`prompt_version`、`generated_at`、`evidence_review_ids`；不得虚构补偿、联系方式或已完成的整改 |
| P0 | 缺少 `POST /api/v1/merchants/{id}/business-suggestions` | 无法生成经营建议及其证据展示 | 前端已提供时间窗、关注特征、低样本/证据冲突提示和可展开证据区 | 每条建议返回统计周期、置信度、模型/Prompt 版本、证据点评 ID 和证据快照；样本不足或证据冲突时不输出确定性结论 |
| P1 | TK-603-02 三个接口的请求/响应 JSON 尚未在 OpenAPI 中冻结 | 前端暂定字段可能与后端实现不一致，联调存在 400/422 风险 | 类型与 API Client 集中在 `merchant-insights` 模块，便于一次性替换 | 补齐 OpenAPI 请求/响应样例、字段校验、分页/错误码和 401/403/404/422 自动化测试 |
| P1 | 竞品、建议和证据接口尚无公开范围与证据一致性约束 | 可能泄露竞品私有信息，或展示与建议不对应的原点评 | 前端只显示聚合竞品数据，并将证据列表限定为当前商家原点评 | 后端在查询层固定公开聚合范围，证据点评与建议的 `evidence_review_ids` 可验证关联，并通过权限隔离与证据一致性测试 |
| P1 | 没有方面/特征聚合接口 | 特征排行无法覆盖完整时间窗，样本超过 200 条时统计会被截断 | 从点评下钻返回的 `aspect_labels` 中聚合最近 200 条，并标注样本上限 | 提供按时间窗聚合的特征接口，至少返回 label、count、sample_count，并支持下钻条件 |
| P1 | 差评归因只有全时间窗汇总，没有日/周/月变化 | 只能展示归因排行，无法展示差评原因趋势 | 当前展示当前筛选时间窗的汇总排行 | 为归因接口增加 granularity 和 period，或提供 topics/reasons 趋势接口 |
| P1 | 点评下钻只返回数组，没有 total、next_cursor 或稳定分页元数据 | 抽屉最多显示 50 条，无法告知用户完整结果数或继续加载 | 当前限制 50 条，特征采样限制 200 条 | 返回统一分页结构和总量，保证排序稳定，并支持 sentiment、时间、特征和归因过滤 |
| P1 | 分析响应缺少 `model_version`、`prompt_version`、`generated_at`、`evidence_review_ids` | 页面无法展示分析版本和生成时间，也无法完成模型回归追溯 | 不伪造版本字段，只展示样本量和点评证据 | 按 API 规范补齐追溯元数据；点评级结果至少返回当前模型版本和证据关联 |
| P1 | 当前 `review_analyses` 实现与数据库文档的版本化模型不一致 | 无法可靠区分 task_type、当前结果和历史模型版本，重跑可能污染聚合 | 前端只能信任接口当前结果 | 对齐 `review_id + task_type + model_version_id` 唯一约束、`is_current` 切换和 labels/reasons JSON Schema |
| P2 | 低样本阈值没有后端口径 | 前端只能自行以少于 10 条显示“数据不足” | 阈值作为前端展示常量，并始终展示样本量 | 后端在聚合响应中返回 sample_count、minimum_sample_size 和 insufficient_data，统一竞品和单店口径 |
