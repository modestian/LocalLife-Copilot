# TK-301-03 会话记忆实现与优化说明

## 1. 文档目的

本文说明 ST-301“可溯源多轮 RAG 推荐”下 TK-301-03 的落地方式。对应验收目标是：相同 `conversation_id` 能恢复当前有效历史；上下文超过窗口后生成受控摘要；执行 `truncate` 后不再向 Agent 提供被截断消息；Redis 丢失时仍可从 MySQL 恢复。

## 2. 本次实现范围

- Agent 层新增 `ConversationMemoryService`，输出模型可直接使用的 `MemoryWindow`：持久摘要、最近原文消息、摘要水位和估算 Token 数。
- 上下文同时受 `context_turns` 和 `token_limit` 约束，旧消息进入摘要，最近消息保留原文。
- 摘要通过 `ConversationSummarizer` 端口适配；默认实现为可重复、无外部依赖的受控摘要器，后续可替换成模型摘要器。
- 摘要元数据持久化在 MySQL `conversations.settings_json._memory_summary`，Redis 只缓存最近消息，不作为事实源。
- `memory_backend=REDIS` 时优先使用 Redis，缓存未命中、损坏或不可用时回源 MySQL；`memory_backend=MYSQL` 时完全绕过 Redis。
- `truncate` 改为移动 `current_branch_message_id`，不删除消息及引用；后续消息默认以当前分支头作为 `parent_message_id`。
- 会话读取只返回当前分支祖先链，被截断的旧分支不再进入列表、摘要或 Agent 上下文。

## 3. 相对原设计的可靠性优化

### 3.1 从“删除后续消息”优化为“不可变历史 + 分支指针”

原数据层实现会在 `truncate` 时物理删除目标消息之后的消息和引用。这与具体设计中的“不物理删除历史”不一致，也会丢失审计、反馈定位和问题复盘依据。

本次改为逻辑分支：

```text
m1 → m2 → m3（旧分支，仍持久化）
       └→ m4（truncate 到 m2 后产生的新分支，当前分支头）
```

当当前分支头是 `m4` 时，只恢复 `m1、m2、m4`，不会使用 `m3`。旧消息和对应引用仍在 MySQL 中，可用于审计或未来的分支查看能力。

### 3.2 从“Redis 默认依赖”优化为“后端显式选择 + MySQL 事实源”

原缓存实现无论 `memory_backend` 设置为何都会访问 Redis。本次明确两条路径：

| memory_backend | 读取规则 | Redis 故障行为 |
| --- | --- | --- |
| `REDIS` | 验证 owner 后读取热缓存，失败回源 MySQL | 对会话恢复无影响 |
| `MYSQL` | 直接读取 MySQL | 不访问 Redis |

owner 校验始终先于缓存读取，避免通过缓存键绕过会话归属校验。

### 3.3 从“仅最近 N 条”优化为“轮数与 Token 双限 + 摘要水位”

仅按消息条数截取无法控制长消息导致的 Prompt 膨胀。本次窗口同时应用：

1. `context_turns × 2` 的消息数上限；
2. `token_limit` 的估算 Token 上限；
3. 至少保留最新一条消息，避免当前问题被摘要替代。

窗口以前的内容生成摘要，并记录 `through_message_id` 与 `through_sequence_no`。相同水位重复恢复时直接复用摘要；窗口前移时只把新增越界部分与旧摘要合并，避免无意义的重复摘要调用。

### 3.4 摘要失效规则显式化

`truncate` 会清除 `_memory_summary`，下一次恢复仅根据新分支重新生成摘要。因此旧分支的偏好、约束或回答不会通过摘要“幽灵般”回到新分支。

默认受控摘要器仅保留：

- 用户明确表达的内容；
- 尚待回答的助手追问；
- 已有合法摘要。

它不会持久化工具载荷、检索证据全文、系统提示词或模型推理过程。生产环境如替换为模型摘要器，仍必须遵守这一输出边界。

### 3.5 内部元数据与外部设置隔离

`_memory_summary` 使用下划线保留命名：

- 创建会话时忽略客户端提交的下划线设置，防止伪造摘要水位；
- API 返回会话设置时过滤内部字段，避免把内部记忆元数据当作用户设置暴露；
- 只有服务端记忆流程可更新该字段。

## 4. 持久化格式

摘要当前复用 `settings_json`，避免为本任务额外引入迁移，同时保持 MySQL 可恢复性：

```json
{
  "_memory_summary": {
    "text": "用户：希望找安静、预算 100 元以内的日料。",
    "through_message_id": "019...",
    "through_sequence_no": 8
  }
}
```

若后续需要多分支同时维护独立摘要或保留摘要版本历史，应新增 `conversation_memory_snapshots` 表，以 `(conversation_id, branch_head_message_id, through_message_id)` 建唯一约束；当前单活动分支需求无需提前增加表复杂度。

## 5. 恢复与截断流程

```text
恢复：owner 校验 → 选择 Redis/MySQL 适配 → 读取当前分支 → 应用轮数/Token 窗口
     → 复用或生成摘要 → 摘要持久化 → 输出 MemoryWindow

截断：owner 校验 → 校验 message_id 属于会话 → 移动当前分支指针
     → 清除摘要水位 → 失效 Redis → 后续读取仅沿新分支祖先链
```

## 6. 兼容性与边界

- 对早期没有 `parent_message_id` 的线性历史，按 `sequence_no <= 当前分支头` 兼容恢复。
- `sequence_no` 仍是会话内全局递增序号；创建新分支不会复用旧序号，因此幂等和唯一约束保持有效。
- 消息和引用继续以 MySQL 为事实源，Redis 清空不影响关键事实恢复。
- 当前仅维护一个活动分支指针；展示和切换多个历史分支不属于 TK-301-03 范围。

## 7. 自动化验证

本任务补充并覆盖以下场景：

- 长会话形成摘要和最近原文窗口，摘要水位写入持久层；
- 相同摘要水位恢复时不重复调用摘要器；
- 窗口前移时增量合并摘要；
- truncate 后 Redis 热缓存失效；
- 新分支不包含被放弃分支消息；
- 无 parent 的存量线性消息兼容恢复；
- `memory_backend=MYSQL` 时完全绕过 Redis；
- Redis 未命中、故障和缓存损坏时继续从 MySQL 恢复消息与引用。
