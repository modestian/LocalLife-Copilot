# 大众点评 AI 智能助手需求分析

本项目旨在打造一个基于 LangChain、OpenSearch 和 Transformer LoRA 的本地生活 AI 助手，为用户提供可信可溯源的智能探店推荐，并帮助商家实现口碑分析与经营优化。

## 1. 分析范围与原则

本文将原始产品需求与课程项目要求合并，遵循以下原则：

- 业务主线采用“3 公里生活圈探店与商家口碑分析”。
- 技术主线采用“知识库 + OpenSearch 混合检索 + RAG/Agent + LoRA 微调”。
- 优先保证端到端闭环、可演示和可量化验收，再实现高难扩展能力。
- 所有 AI 结论均应可追溯、可反馈、可评测。

## 2. 业务问题分析

### 2.1 用户侧

- 传统筛选只能处理固定条件，难以理解氛围、场景、同行人员等语义需求。
- 点评数量多、内容重复且观点冲突，用户归纳成本高。
- 生成式推荐若不展示依据，用户难以判断可信度。

### 2.2 商家侧

- 中小商家缺少专业工具持续追踪评价情绪和问题趋势。
- 差评回复、竞品研究和经营总结耗时，且输出质量不稳定。
- 点评数据未形成可执行的经营建议。

### 2.3 平台侧

- 商家、菜单、点评和运营内容来源异构，更新状态不一致。
- 违规内容、刷单和热点事件依赖人工排查，效率有限。
- 模型、提示词、数据和用户反馈之间缺少可回归的迭代闭环。

## 3. 角色与权限

| 角色 | 数据范围 | 核心权限 |
| --- | --- | --- |
| 普通用户 | 公开且有效的商家与点评、自有会话 | 搜索、对话、收藏、反馈、查看引用 |
| 商家用户 | 绑定商家及公开竞品汇总 | 查看口碑、生成回复、提交反馈，不得查看竞品私有数据 |
| 区域运营 | 被授权区域 | 审核内容、管理热词热榜、查看区域统计 |
| 知识库管理员 | 被授权知识库 | 上传、编辑、重建索引、管理文档和规则 |
| 平台管理员 | 全平台 | 用户角色、模型、系统参数、审计和发布审批 |

权限模型采用 RBAC + 资源范围（知识库、商家、区域）组合授权，后端必须在接口层和数据查询层同时限制范围。

用户侧权限边界：所有已登录账号共享“公开且有效”的探店知识语料；会话、消息与反馈仍按 `user_id` 私有隔离。RBAC 与知识库资源授权用于上传、编辑、删除、重建索引等后台管理操作，不得阻断普通用户使用公共语料发起探店对话。公共语料的 tenant、knowledge base 与 resource scope 必须由服务端解析和注入，不能信任前端传值。

### 4.6 史诗 F：Transformer LoRA 微调闭环

| ID | 需求 | 优先级 | 可验证结果 |
| --- | --- | --- | --- |
| FR-F01 | 反馈收集 | Must | 支持赞/踩、修正答案，关联 conversation_id 与 message_id |
| FR-F02 | 数据集生成 | Must | 可按评分、时间、任务类型导出脱敏 JSONL |
| FR-F03 | LoRA 训练 | Must | 使用 Transformers + PEFT/LoRA 完成至少一个领域任务微调 |
| FR-F04 | 评测与审批 | Must | 与基础模型使用同一测试集对比，保存指标和模型卡 |

首期推荐微调“点评情感与差评归因”分类模型，原因是标签结构清晰、算力成本可控且指标容易量化。若资源允许，再对小型指令模型进行商家回复生成 SFT LoRA。

## 5. 关键业务流程

### 5.1 数据入库

数据源登记 → 文件/数据抽取 → DataFrame 标准化 → 清洗与去重 → 结构化行转文本 → 文本切分 → Embedding → MySQL 元数据落库 → OpenSearch 原子化写入 → 质量抽检 → 发布。

### 5.2 对话推荐

鉴权 → 内容安全检测 → 会话恢复 → 意图路由 → 条件抽取/必要时追问 → 混合检索 → 权限与业务过滤 → RRF/加权融合 → 可选重排 → RAG 生成 → 引用校验 → 输出安全检测 → 流式响应 → 日志与反馈入口。

### 5.3 LoRA 迭代

用户/商家反馈 → 脱敏和质量筛选 → 数据集版本固化 → 训练/验证/测试切分 → LoRA 训练 → 基准评测 → 人工抽检 → 模型登记 → 灰度发布 → 线上指标监控 → 回滚或全量发布。

## 6. 非功能需求

### 6.1 性能

- P95 API 处理耗时（不含 LLM 生成）低于 500 ms。
- OpenSearch 混合检索 P95 低于 300 ms（演示数据规模下）。
- 首包时间低于 2 秒；WebSocket 心跳间隔不大于 30 秒。
- 文件上传采用分块或流式读取，单文件默认上限 100 MB，可配置。

### 6.2 可用性与一致性

- 核心服务健康检查可被 Compose/Nginx 读取。
- 索引任务需幂等；重复导入不能产生重复 chunk。
- MySQL 为业务元数据事实源，OpenSearch 为可重建搜索投影。
- 文档变更通过版本号和 outbox 事件驱动索引更新，失败可重试。

### 6.3 安全与隐私

- 密码使用 Argon2id 或 bcrypt；访问令牌短时有效，刷新令牌可撤销。
- API Key、数据库密码和模型密钥只能通过环境变量/Secret 注入。
- 上传文件校验扩展名、MIME、大小和恶意内容；文件名随机化保存。
- 查询必须包含 tenant/knowledge_base/resource_scope 过滤，不得依赖前端隐藏。
- 训练数据必须脱敏并记录授权来源；日志禁止记录明文密码、Token 和完整密钥。
- LLM 生成代码只能在独立容器中执行，并设置无网络、非 root、只读文件系统、CPU/内存/时间限制。

### 6.4 可维护性

- 通过 FastAPI 自动生成 OpenAPI，接口统一版本前缀 `/api/v1`。
- 后端核心逻辑单元测试覆盖率不低于 70%。
- 日志采用 JSON 格式，包含 trace_id、user_id、conversation_id 和 latency_ms。
- 数据库变更必须由 Alembic 迁移管理，禁止生产环境手工改表。

## 7. 数据与模型质量要求

| 指标 | 计算口径 | 目标 |
| --- | --- | --- |
| Recall@5 | 标准问题的相关商家是否出现在前 5 | ≥ 0.80 |
| MRR@10 | 首个相关结果倒数排名均值 | ≥ 0.65 |
| 引用正确率 | 引用片段确实支持回答的比例 | ≥ 0.95 |
| 兜底准确率 | 无证据问题正确拒答比例 | ≥ 0.90 |
| 情感 Macro-F1 | 正/中/负三分类 | ≥ 0.80 |
| LoRA 增益 | 同测试集相对基线的 Macro-F1/任务指标 | 目标 ≥ +0.03，且不得退化 |

## 8. 约束、假设与风险

| 项目 | 说明 | 应对策略 |
| --- | --- | --- |
| 数据授权 | 不假设拥有真实大众点评全量数据 | 使用授权数据、公开样例或自建脱敏演示集 |
| 数据新鲜度 | 营业信息和菜单可能过期 | 记录 valid_from/valid_to、last_verified_at，检索时过滤 |
| 模型幻觉 | LLM 可能生成无依据事实 | 证据阈值、引用校验、结构化约束和兜底 |
| 算力有限 | 大模型全参训练不可行 | 量化加载 + LoRA/QLoRA，首选小型分类任务 |
| OpenSearch 一致性 | 索引为最终一致 | outbox、任务重试、对账和可重建索引 |
| 团队并行冲突 | 四人同时修改公共模块 | API/Schema 先行、代码所有权、短分支和每日集成 |

## 9. 验收范围

项目验收以“可复现演示 + 自动化证据”为准：

1. 在全新环境执行 Docker Compose 后可完成初始化和健康检查。
2. 上传一组商家/点评数据后，可查询任务进度并在 OpenSearch 检索到。
3. 用户提出复合条件问题，系统能追问、推荐、展示来源并处理无结果情况。
4. 商家端展示情感分布、趋势和差评归因，可跳转到原评价。
5. 反馈可进入数据库并导出 JSONL；LoRA 训练产物、配置和前后评测可复现。
6. 关键接口具备权限、参数、异常、幂等和并发测试。
